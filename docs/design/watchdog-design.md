# watchdog 总体设计

本文是 watchdog 强制层（`hooks/` + `monitors/`）的**设计依据**：它要解决什么问题、按什么原则演进、现在由哪些部件组成、每条告警怎么被正确地清掉。逐个脚本的契约见 `hooks/README.md`，主 agent 的义务见 `skills/execute-task/SKILL.md` `## Watchdog 强制层`。三处口径冲突时以本文的原则为准，再回头修正另外两处。

## 1. 要解决的问题

长任务里主 agent 会派出很多执行者（subagent、teammate、后台任务、外部批跑），然后停下来等。等待本身是正常的，问题在于：**任务停住时，外面看不出它是「在正当地等」还是「已经没人在推了」**。后者的形态在实战里反复出现：

- 角色被 API 错误杀死（SubagentStop 不触发，结果永远不会送达）；
- 角色或后台任务结束了，完成通知没送到主 agent；
- 角色以「等待通知」收尾，它启动的后台进程没人再看；
- 主 agent 以为「某条通道还在跑」，其实早已结束；或者说了要派发却没派发、自己也没在做；
- 整个会话没有任何人在动，但宿主的后台任务列表里还挂着一堆已经不会再推进任务的条目。

同时，正当的停止必须安静：等用户回答、等用户批准设计、等一个声明过的长跑任务、任务已经交付等确认。

所以 watchdog 只回答一个问题：**这个任务现在有没有人在推？没有的话，是不是有一个说得清、会过期的理由？**

## 2. 设计方向：agent 主导，插件做工具与保障者

这是长期维护目标，所有后续改动都按它取舍。

**背景。** 0.25～0.31 的每一版几乎都是「出了一个问题，补一个洞」：先给等用户加豁免（main-state），再给 AskUserQuestion 加豁免、给 cwd 漂移加兜底、给无执行者加检查、给常驻后台任务加声明……每补一种正当的安静场景，就要在脚本里硬编码一条判断。正当场景是穷举不完的，硬编码的判断会互相叠加、彼此冲突，最后没人能说清一条告警为什么响、为什么不响。

**方向。** 把「这个任务现在为什么安静」的判断权交给最了解情况的主 agent，插件退到两个角色：

1. **工具。** 插件给主 agent 提供表达意图的接口：`expect.sh`（声明在等什么、等到什么时候、哪些后台任务是常驻的、按任务放宽阈值）、`Current Phase`（任务处在哪个阶段）、`task-pointer.sh`（哪些任务归本会话）、`agent-runtime-state.sh`（确认角色死亡、对账）。主 agent 在不同的时机自己选择设置什么状态、什么参数。
2. **监测者与保障者。** 插件不信任主 agent 一定会做对——watchdog 存在的意义就是防止主 agent 犯错导致任务停住。插件观察主 agent 改不了的**事实**，守住几条主 agent 覆盖不了的**不变量**（§4）。声明只能解释安静，不能让检查永久失效。

**这意味着：**

- 遇到新的正当安静场景，**先问「主 agent 能不能声明它」**。能，就复用或扩展一种声明（加一个 kind、一个参数），而不是在脚本里加一条针对这个场景的豁免。只有主 agent 自己无法知道的事实（宿主后台任务列表、工具调用活动、API 错误、用户是否刚发过言）才写进代码。
- **允许误报，但误报必须能自愈。** watchdog 宁可多叫一次，也不能漏掉一次停摆。但每条告警都必须告诉主 agent：怎么确认、确认是误报之后用哪条声明让它不再响。主 agent 照做之后，同一个原因不应该再次触发。一条告警如果没有正当的清除办法，它就是设计缺陷。
- **兜底要有一条与平台、与角色类型无关的底线。** 细粒度的检查（逐角色存活、终态未收取）依赖平台能力，覆盖面有限；底线检查只依赖「有没有人在调用工具」这一个所有平台都有的事实。

## 3. 三类输入

| 类别 | 是什么 | 谁写 | 主 agent 能改吗 |
|---|---|---|---|
| **事实** | 工具调用活动（`runtime/activity`）、用户发言时刻（`runtime/user-prompt-epoch`）、主 agent 的对话框状态（`runtime/main-state`）、Stop 时宿主报告的后台任务（`runtime/stop-snapshot`）、API 错误中断记录（`runtime/api-failures/`）、fixed-pack 角色记录（仅 Linux） | hook / monitor | 不能 |
| **声明** | `## Agent State` 里的 `Expect`（`wait` / `user [--watch]` / `resident`）与 `Tune` 行 | 主 agent 用 `expect.sh` | 能，但每条都会过期 |
| **阶段** | `Current Phase`：`design` / 活跃阶段（implementation、testing、review、delivery）/ `observing` / `awaiting-confirmation` / 终态 | 主 agent | 能 |

`main-state` 的四个取值是对话框事实，不是推断：

- `working`：主 agent 正在调用工具，或用户刚发言。
- `awaiting-user`：一个**正在打开**的用户对话框——AskUserQuestion、权限确认、MCP elicitation、`agent_needs_input`。行里记着它的归属者（`main` 或某个 subagent 的 `agent_id`），只有归属者自己的下一步才关闭它；别的 agent 照常干活不会让它被当成已关闭。
- `idle`：这一轮已经结束（Stop，或主 agent 这一轮因 API 错误结束），或宿主报告「上一轮结束约 60 秒、其间用户没有操作」（`idle_prompt`）。
- `ended`：会话结束。

`idle_prompt` 记成 `idle` 而不是 `awaiting-user`：它说的是「停下了、用户走开了」，和有没有对话框无关（宿主在屏幕上有对话框时不发它）。把它当成「在等用户」，主 agent 每次停下、用户走开一分钟后都会被当成在等用户（0.32.0 之前就是这样），任何尊重对话框的检查都会被它静音。

## 4. 不变量（主 agent 覆盖不了）

- **I1 有人在推，或者有理由。** 活跃阶段的任务，要么有人在动（工具调用活动、宿主报告的执行者），要么有一条有效的声明说明在等什么；两者都没有就报警。
- **I2 每条声明都会过期。** `wait` 到点、`user` 在用户下次发言时、`wait --ref` 在它绑定的后台任务结束时、`Tune` 有上限。不存在永久静音。
- **I3 事实优先于声明。** 声明说在等的后台任务已经不在宿主列表里，以列表为准。
- **I4 硬失败一定会被报告。** subagent / teammate 的 API 错误中断，每条都会送到主 agent 一次；主 agent 自己那一轮的失败由会话静默带出（主 agent 有有效声明时不报——它已经说清楚在等什么，到点的声明会叫醒它）。
- **I5 每条告警都可以被正确清除。** 告警里写明确认方法和清除办法；按办法处理之后，同一原因不再触发。

## 5. 告警目录

「层」：L1 = PostToolUse 注入，L3 = 后台 monitor 唤醒，L4 = Stop 时拦截。

| 告警 | 层 | 触发 | 被什么压住 | 怎么清除 | 重复节奏 |
|---|---|---|---|---|---|
| **会话静默**（0.32.0） | L3 | 活跃阶段、还有活，整个会话（主 agent、subagent、teammate）已 `silence-sec`（默认 1 小时）没有任何工具调用，用户也没发言、状态文件也没写 | 有效的 `wait` / `user`（`--watch` 的不算）；旧格式 `Waiting On`；打开着的用户对话框；上次 Stop 时排着的宿主唤醒（`silence-sec` 之后再宽限 1 小时）；无执行者条件成立（含其冷却中） | 核实各通道，死了的续做重派；确实在等不调用工具的东西就 `wait --at`，或自己定静默时长 `tune silence-sec / remind-sec`（各最多 24 小时）；等用户就 `user`；已交付就改阶段 | 每 `remind-sec`（默认 30 分钟）唤醒一次；叫醒后无动作才升级通知用户（§5.1） |
| **API 错误中断**（0.32.0） | L3 | 宿主报告某个 subagent / teammate 的这一轮因 API 错误结束（StopFailure） | 无（事实） | 核实是否已处理过；没处理的按续做重派；同一错误反复出现时先声明 `wait` 并告诉用户 | 每条记录报一次，冷却（600 秒）内的多条合并成一行 |
| 无执行者 | L4 + L3 | 活跃阶段还有活，停下时宿主报告没有执行者（L3：停下 `no-executor-sec` 后仍如此） | 有效的 `wait` / `user`；旧 `Waiting On` | 派发下一步；核实通道；声明 | L4 每次停下（冷却 600s）；L3 冷却 900s |
| 声明到点 | L3 | `wait` 的时间到了 | 无 | `clear` 或用新时间重新 `set` | 每 `remind-sec`；叫醒后无动作才升级通知用户 |
| 声明绑定的后台任务已结束 | L3 | `wait --ref` 的任务不在上次停下时的列表里 | 无 | 读结果后 `clear`，或换 id 重新 `set` | 一次 |
| 观察期无排定检查 | L4 + L3 | `observing` 阶段没有任何会把主 agent 叫回来的东西 | 有效 `wait` / `user`；宿主排定的唤醒 | `wait --at` 或改成 `done` | L3 每 3 小时 |
| 状态文件过期 | L1 / L4 / L3 | 活跃阶段 `status.md` 超过 600 / 1200 / 1800 秒没写 | `wait`；旧 `Waiting On`；main-state 为 `awaiting-user` / `idle`（L3/L4） | 写状态文件 | 各层冷却 |
| 角色静默 / 跟踪未对账 / probe 逾期 / 无输出 / 终态未收取 | L4 + L3 | fixed-pack 观察（仅 Linux，仅三种 zyz-worker 角色名） | 无 | `probe-*` / `finalize` / `reconcile-*`；读结果并写状态 | L3 冷却 900s，6 小时后不再看 |
| 未启用 | L3 | 有未完成任务目录却解析不到本会话的指针 | — | `task-pointer.sh arm` | 一次 |

「状态文件过期」是**卫生**提醒，不是存活检测：主 agent 停下后 main-state 就是 `idle`，它不再响。停下之后判断「有没有人在推」的，只有会话静默、无执行者、声明到点三条，以及 Linux 上的角色级检查。

### 5.1 IM：只在需要人的时候发（0.32.0）

唤醒主 agent 和通知用户是两件事。**任务还在执行时，所有问题先交给主 agent**——它停下、subagent 走一步、subagent 因 API 错误死掉，都由 watchdog 叫醒它处理；用户只在三种时刻收到 IM：

| 时刻 | 类别 | 来源 | 去重 |
|---|---|---|---|
| **需要用户回答** | `needs_input` | 对话框打开（权限确认、elicitation）；AskUserQuestion；主 agent 声明 `user`（用自然语言提问，含 `--watch`）；兜底：主 agent 在 design 阶段停下、宿主报告没有执行者、也没有 `user` 声明（多半停在设计批准闸门却忘了声明） | 提问类延迟 60 秒，期间用户已回复就不发 |
| **任务交给用户** | `completed` | 进入 `awaiting-confirmation` / `observing` / 终态（Stop 时判断） | 每次进入一次 |
| **主 agent 自己处理不了** | `failed` / `stuck` | 主 agent 自己这一轮因 API 错误结束；或 watchdog 叫醒主 agent 至少 10 分钟后再报时会话里仍无任何动作（升级） | 升级：同一段停摆每个任务一次，有进展即重新计 |

这条规则也是 §2 的直接应用：**主 agent 的声明和阶段直接决定用户会不会被打扰。** 声明 `user` 就是告诉插件「这里需要人」，改成交付阶段就是「交给人了」。「问用户、但还有别的活」由 `user --watch` 表达：发 IM，但什么都不压，watchdog 照常盯着。插件守的底线是升级——主 agent 叫不醒、或叫醒了也不动，用户一定会知道。

每条 IM 带会话名称（Claude Code 的 `/rename` 名或 AI 标题，Codex 的线程名），用户能直接找到该打开哪个会话。

## 6. 平台能力

| 能力 | Claude Code / Linux | Claude Code / macOS | Codex |
|---|---|---|---|
| 会话静默、API 错误中断 | ✅ | ✅ | 只写诊断日志（没有 monitor 唤醒通道）；IM 升级照常——没人读日志，第二次报告就会通知用户 |
| 无执行者、声明到点、观察期 | ✅ | ✅ | L4 部分 fail open（输入没有 `background_tasks`） |
| 角色级检查（fixed-pack） | ✅（仅三种角色名） | ❌ `genesis-capability-unavailable` | ✅ |
| 状态文件过期、L2 / L5 / L6 | ✅ | ✅ | ✅ |

两条底线检查不依赖 fixed-pack，也不依赖角色名：用 `name` 派发的 agent team teammate（`agent_type` 是名字，匹配不上 `review-agent` 这类 matcher）同样会被覆盖——它们的工具调用 hook 照常触发，带着 `agent_id`。

## 7. 现状梳理：冲突与重复（0.32.0）

逐条核对 0.25～0.31 累积下来的机制后的结论与处置：

1. **`awaiting-user` 混进了 `idle_prompt`（冲突，已修）。** 原来 `idle_prompt` 也记成 `awaiting-user`，于是每次停下一分钟后状态都是「在等用户」。它本身不影响状态过期（`idle` 同样压制），但让 `awaiting-user` 失去了「真的有个对话框开着」的含义，任何想用它压制停摆检查的地方都会变成永久静音。现在 `idle_prompt` 记 `idle`。
2. **Stop 的「awaiting-user 不被覆盖」豁免（冲突，已删）。** Stop 意味着这一轮已经结束，任何对话框都已关闭，保留 `awaiting-user` 只会留下一个过期的状态。现在 Stop 一律记 `idle`。
3. **无执行者 vs 会话静默（互补，不重复）。** 无执行者是快而精确的检查（停下时宿主说没人），会话静默是慢而通用的底线（不管宿主列表说什么，真的没人在动）。两者共用同一组声明压制；同一轮扫描里无执行者已经报了，会话静默就不再报。
4. **角色级检查 vs 会话静默（分层，不重复）。** 角色级检查能点名哪个角色出了问题，但只在 Linux、只认三种角色名；会话静默是所有平台、所有执行者类型都适用的底线，只能说「没人在动」。
5. **状态文件过期的三层阶梯（刻意，不是重复）。** 600s 注入 → 1200s 拦截 → 1800s 唤醒，强度递增，见 `docs/architecture.md` §4.3。
6. **IM 与唤醒主 agent 是两条通道（刻意）。** IM 告诉用户，monitor 行叫醒主 agent。0.32.0 之前 StopFailure 只走了 IM：用户在睡觉，主 agent 永远不知道——这是本次补上的缺口。
7. **旧格式 `Waiting On` 有一个独立的严格校验器（已知重复，冻结）。** `lib.sh zyz_status_waiting` 与 `expect_state.py` 各解析一遍旧行：前者决定压制（1 小时上限、任一行畸形则整组无效），后者只产出到点提醒。`expect.sh` 从 0.30.0 起不再写旧行，它只存在于老任务目录里；它的边界语义有 30 多条测试钉住，合并只会改写这些测试而不改变任何行为。处置：冻结，不再给它加任何功能；所有新声明一律走 `Expect` 行；等老任务目录不再需要时整体删除。
8. **IM 与唤醒的重叠（冲突，已修）。** 0.32.0 之前两条通道同时发：主 agent 每次停下都发 `idle`，watchdog 的每条发现也同时发 `stuck`，于是 subagent 走一步、主 agent 收到结果正常推进，用户也被打扰；`idle_prompt` 还被折叠成 `completed` 再发一次。现在按 §5.1：执行中的问题只叫醒主 agent，用户只在需要人、任务交付、主 agent 处理不了时收到 IM；`idle` 类别删除，watchdog 的 IM 改为升级（取代原来散落在各处的「第 3、5 次」「第 1、3、5 次」计数）。

## 8. 已知盲区（如实说明）

- **整个进程死亡**（kill、OOM、关终端、宿主机重启）：所有 hook 和 monitor 一起没了，本层无能为力。需要会话外的守护进程（`self-healing-loop` 的 cron 半边就是这种形态）。
- **主 agent 自己反复撞同一个 API 错误**（余额不足、鉴权失效）：会话静默在 1 小时后叫醒它、之后每 30 分钟一次，每次唤醒都会再失败一次；用户在失败当时收到 `failed`，叫醒无果后再收到一次升级的 `stuck`。插件不替主 agent 判断「这个错误会不会自己好」。
- **subagent 的权限确认通知不带 `agent_id` 时**会被当成主 agent 的对话框：主 agent 停着时，它要等主 agent 下一次动作或用户发言才关闭，其间会话静默不响。
- **teammate 的 hook 归属**：teammate 的工具调用 hook 按会话 id 找指针。如果某个宿主版本给 teammate 的 hook 传了不同的会话 id，它的活动就看不见，会话静默会多报——按 §2，这次误报由主 agent 用 `wait` 声明清掉。
- **多任务会话**：会话静默对每个活跃任务各报一条——每个任务都要各自说明为什么安静，一个任务上的声明不替别的任务说话。
- **长时间只思考不调用工具的执行者**：超过 `silence-sec` 会被当成静默。用 `wait --at` 声明，或用 `Tune silence-sec` 放宽（最多 24 小时）。
- **设计批准闸门忘了声明 `user`**：兜底的 `needs_input` 要靠 Stop 输入里的 `background_tasks` 判断「没有执行者」；Codex 没有这个字段，兜底不响，用户只能靠声明得知。
- **用户就在终端前**：提问类 IM 延迟 60 秒、期间回答就不发；超过 60 秒才回答，仍会多收一条。

## 9. 改动时要遵守的规则

- 新的正当安静场景：先扩展声明，不加硬编码豁免（§2）。
- 新的告警：必须在 §5 的表里写清触发、压制、清除办法、重复节奏，并在告警文本里给出清除命令。它先叫醒主 agent；给用户的 IM 只能落在 §5.1 的三种时刻之一（watchdog 的发现一律走 `notify_stuck` 升级），不在告警处另发。
- 新的事实来源：写进 §3，说明谁写、何时失效、缺失时 fail open 还是 fail closed。
- 改阈值或文件路径：本文、`hooks/README.md`、`SKILL.md` `## Watchdog 强制层` 三处同改（`docs/architecture.md` §8）。

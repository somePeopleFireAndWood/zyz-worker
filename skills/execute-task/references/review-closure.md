# 评审收口细则

`SKILL.md` `## 评审收口` 的细则。适用于每个档位、每个评审点（设计、实现 / lane、汇总）和每个评审者（reviewAgent、跨 harness）。

## 为什么

停止条件如果是"对抗性评审者再也找不出问题"，这就是一个无界搜索：每次修复只回应一种构造，下一轮又会找到同一类问题的下一个变体。一个令牌脱敏 SubTask 从第 10 轮评审一直跑到第 20 轮，后面几轮回应的是会抛异常的 `__str__`、重写了 `strip` 的 `str` 子类、一千层深的异常链——评审者自己一直把它们标为刻意构造，工作流却没有规定何时停。复盘数据：评审循环占重型任务活跃时间的 48%–60%；32% 的 blocking 修复没有改变产品行为（测试强度 13%、文档同步 9%、证据流程 8%）；实现阶段的真缺陷第 1 轮 58 条、第 2 轮 17 条、第 3 轮及以后 4 条；收口检查 6 个该做的点只做了 1 个。所以收口用事先约定、有限的退出条件，并由脚本强制。

## 1. 评审点

- 设计和实现都把**主路径**设为一个评审点，每个**附属子功能**各一个，各自计轮次；附属子功能不拖住主路径的关闭（复盘里约一半的设计 blocking 集中在附属子功能上）。汇总评审是一个单独的评审点。
- 用 `review-round.sh open <point> --stage design|impl|aggregate [--kind main|aux] [--tier standard|strict]` 登记。`<point>` 用 `[a-z0-9-]+`，例如 `design-main`、`design-replay`、`impl-st2`、`aggregate`。
- **单个评审点升档**：`--tier` 只能比任务级 `- Tier:` 更严；该评审点的上限、`mode`、`cross-harness` 都按它自己的生效档位算（`review-round.sh status <point>` 显示）。已经打开的评审点要升档，用 `open <point> --tier …` 重新打开。重开一个已关闭的评审点时保留它原来的单点档位；降档无论走哪条路径（`open --tier`、`tier`）都要求 `--by user`。
- 发现可以在评审点之间移动：主路径评审里出现的附属子功能问题，归到该子功能的评审点。

## 2. 轮次与模式

- **第 1 轮全量。** 评审者覆盖该评审点的全部范围，按覆盖维度登记。
- **第 2 轮起增量。** 输入是上一轮被接受的 blocking 清单、修复的 diff（和对应的提交范围），以及上一轮被拒绝或降级的 blocking 及理由。评审者的任务有三项：逐条核实修复已落地；评审这份 diff 是否引入了新问题（复盘里有 15 条 blocking 是上一轮修复引入的）；对每条被拒绝的 blocking 二选一——在报告的 `## 已复核的被拒绝建议` 里认可这次拒绝，或重新提出为 blocking。增量轮不重新评审未改动的代码。作者裁决自己产物的发现时，这一项就是"作者不当自己的裁判"的保障。从第 2 轮起（含 `start --full` 开的全量轮），评审者给每条新发现注明来源：`原有`（之前就有、前几轮没报），或 `上一轮修订带出`（含只落地一半的修复）；裁决者核对后用它填 `result --induced`。
- **全量复审**只在汇总评审时做，或者某次修复大到改变了结构时做（换了机制、移动了模块边界、重写了主路径）。后者由主 agent 判断，用 `review-round.sh start <point> --full --reason <改了什么结构>` 强制本轮 `mode=full`；impl 评审点的全量轮 `cross-harness=yes`，aggregate 评审点只有第 1 轮是 `yes`（`--full` 开的 aggregate 轮也是 `no`）。轮次照常计数，上限不变。
- **每一轮都重新派发 review-agent。** 不把评审者留作常驻 teammate、下一轮用 SendMessage 续用：那样会绕开 `review-gate.sh` 和 L5。同一轮里的中途重派（评审者死掉、按维度并行派多个 reviewer）发生在 `result` 之前，照常允许；最新一轮已经 `result` 后，`review-gate.sh` 拒绝用同一标记再派发，先 `start` 新的一轮。
- 每轮都先运行 `review-round.sh start <point>`（上一轮要已 `result`，否则 exit 3），它输出 `round=<n> mode=full|incremental cross-harness=yes|no`；派发 review-agent 时 prompt 里写一行 `review-point=<id> round=<n> mode=<full|incremental>`，另起一行 `Tier: <fast|standard|strict>`（评审点的生效档位，`review-round.sh status <point>` 显示）。`review-gate.sh` 核对这两行；L5 范围守卫对带 `mode=incremental` 的派发放行。增量复审的范围由本节定义，它不是缩范围；评审者在这个范围内照常报告每一条发现。"恢复卡住的角色时缩减范围"仍然禁止（`references/recovery.md`）。
- 本轮结束后运行 `review-round.sh result <point> --blocking N --rejected R --induced I --pending P [--behavior M]`：
  - `N` 是本轮被接受的 blocking 条数；`R` 是评审者报告为 blocking、但被裁决者拒绝或降级的条数（`Review` 行记为 `rejected=<n>`）；`M` 是 `N` 里会改变产品行为的条数。
  - `I` 是本轮 blocking（被接受的加被拒绝的）里由上一轮修订带出的条数，含只落地一半的。
  - `P` 是这个评审点此刻仍在等用户回答的 blocking 条数（§5 第 3 条），包括更早轮次提出、还没回答的。它是当前状态，不是本轮 blocking 的子集，所以不和 `N + R` 比大小：评审者按派发不重复报告待定项，这些项不再计入之后各轮的 `--blocking`，只通过 `--pending` 体现，直到用户回答并改完。用户回答后：要改设计的，改动进下一轮增量复审，那一轮的 `--pending` 填还剩几条；回答不需要改动设计的，用 `result` 重填这一轮，`--blocking`、`--rejected`、`--induced` 照原值再给一遍，`--pending` 写 `0`。最近一轮 `pending` 大于 0 时 `close --outcome passed` 被拒绝，`start` 不受影响。
  - 有档位的任务从第 2 轮起，`--rejected`、`--induced`、`--pending` 三个都必填，没有就写 `0`，缺了以 exit 2 拒绝。`result` 每次整行重填，没给的参数回到 `-`；漏写的 `--rejected` 会按 0 参与提前停的比较（§7），所以更正时把所有参数再写一遍。第 1 轮和没有档位的旧任务不要求这三个；第 1 轮不写 `--rejected` 时记为 `-`，`passed` 关不了。`I` 不能大于 `N + R`。下一轮开不了时（到上限、第 2 轮不收敛），`result` 的输出里当场就有 §7 的走势和三个选项。
- **设计评审的修订量。** 设计文档是散文，没有编译器和测试裁决：每轮修订新写的文字越多，下一轮能被挑出的问题就越多，所以每轮新写的量要逐轮变小。design 评审点的 `start` 把本轮被评审的文档（`--docs <path>...`；不给时取 `status.md` 元数据 `- 设计文档:` 一行的路径）复制到 `<task-dir>/reviews/snap/<point>/r<n>/`。从第 2 轮起它与上一轮的快照比较，输出 `delta=+<增行>/-<删行> prev=<+a/-b|-> growing=yes|no`，并把 diff 写到 `<task-dir>/reviews/snap/<point>/r<n-1>-r<n>.diff`（输出里 `diff=` 一行是它的绝对路径），增量复审就用这份 diff。同一评审点每一轮给同一组文档：脚本只比较两轮都采集到的文档，这一轮没有列出的文档不参与比较（输出一行 `note:` 写明是哪几份），它的修订既没有被计量，也不在交给增量复审的 diff 里。`growing=yes`（本轮新增行数比上一轮多）只告警、不拦截：主 agent 先按 `prompts/main-agent.md` 的修订纪律检查这一轮写进正文的东西（非阻断发现、依赖用户回答的部分、可以用减法代替的新机制），再派发。没有可读的文档时跳过。修订量只在设计阶段计量；实现阶段有测试裁决，不计量。

## 3. 声明域

衡量标准是声明域，而不是构造看起来有多怪。每份设计都说明它的范围边界（`templates/design-doc.md` 的 `## 范围边界`；快速档写在 `change-note.md` 的"不在范围"里）：谁调用这次改动、用什么输入，谁可能控制这些输入（威胁模型），以及用户明确排除在范围外的构造。"刻意构造"指的是**在该域之外**：对于一个只接收程序自身异常的脱敏辅助函数，恶意对象属于刻意构造；对于一个运行攻击者提供代码的沙箱，它恰恰在范围之内。

- 范围边界是用户设计的一部分。威胁模型和每一条范围外条款都由用户决定。主 agent 在批准闸门前重新生成快速审阅时，把用户没有亲口说过的条款（首先是威胁模型）作为"在用户未作决定时所做的假设"列入 `### 需要你关注的细节`（快速档列在改法确认消息里），让用户在批准设计时一并批准这把尺。
- 涉及安全或数据的改动缺少声明域、或者声明域含糊时，算 blocking 的"设计缺失"（第 2 类），并标 `requires-user-decision`。
- 设计对此没有说明、而发现又涉及安全或数据时，该构造是否在范围内，是用户设计中的一个歧义，由用户决定（`SKILL.md` `## 用户设计主导权`），而不是评审者或裁决者。
- 设计没有说明、也不涉及安全或数据时，域就是当前调用方实际能产生的输入，通过逐一列举调用方确定。对外暴露的接口面（公共 API、CLI、网络或插件入口）的调用方包括其外部使用者：它的域是文档化的契约，以及这些使用者能发送的所有输入。
- 这种"列举调用方"的兜底只用于对照按原样写成的设计来给健壮性发现分级。设计的正确性所依赖的未陈述前提（上游返回已排序的数据、某字段从不为 null）仍然作为问题交给用户；不能因为今天的调用方恰好满足它，就把它算作 `contrived`。

## 4. 分级与 blocking 准入

每条发现取一个等级：

| 等级 | 含义 | 是否让评审点保持打开 |
|---|---|---|
| `blocking` | 属于下面三类准入之一 | 是 |
| `non-blocking:normal` | 一项真实的改进，但在任何可达输入上都不会产生错误行为：清晰度、可维护性、超出合同所需的测试强度 | 否 |
| `non-blocking:contrived` | 只在声明域之外才会显现——需要叠加两处或更多相互独立的不自然改动，或需要一个任何域内输入都不会产生的恶意对象或状态——**并且**没有任何当前调用方能触达它 | 否 |

**blocking 的准入只有三类：**

1. **可达的产品缺陷。** 在声明域或当前调用方能产生的输入上会影响到产物：主路径缺陷，可复现的安全、正确性、数据或回归缺陷，处理错误的域内边界值。实现评审要附复现：失败的测试、具体输入，或调用路径的 `file:line`。
2. **设计缺失或矛盾。** 指明具体章节，以及缺了什么或哪两处冲突；包括 `../../../subagents/review-agent.md` 列出的设计评审阻断项。
3. **违反合同。** 合同是已批准的设计本身（快速档是 `change-note.md`，标准档和严格档是设计文档），连同其中的验收标准、测试计划和声明域。实现违背已批准设计，或验收标准、测试计划明确要求的东西缺失或不满足（包括合同点名要求的测试缺失），都属于这一类。

**其余发现的去向：**

| 发现 | 去向 |
|---|---|
| 测试强度（代码没错，测试不够强） | `non-blocking:normal`；合同点名要求的测试缺失时按第 3 类处理 |
| 证据或流程缺口（缺坐标、缺变异记录、维度没登记、冻结或哈希问题） | **补证请求**：作者补上，裁决者核对，不开新的一轮，也不计入 blocking 数 |
| 文档同步（快速审阅漂移、引用不同步、措辞） | 主 agent 在设计批准前机械地重新生成一次，不进入评审（`references/design-doc-discipline.md`） |
| 极端构造 | `non-blocking:contrived`，进遗留风险清单 |
| `## 关键机制` 清单可能有遗漏 | `non-blocking:normal` 建议；清单由用户随设计批准，用户可以增删 |

规则：

- **等级只看问题本身。** 三类准入问的是同一件事：按当前设计（或代码）原样实现，在声明域内的真实情况下会不会出错。会，就是 `blocking`；不会，就是非阻断。解法要不要加机制、改动有多大，不影响等级：不因为修起来要加机制就升级，也不因为修起来贵就降级。
- **拿不准时**：可达性不清楚，就按 `blocking` 处理，并写明那个悬而未决的可达性问题。"拿不准"不能用来给证据缺口升级。这一条用在评审者第一次给一条发现定级时；为了加机制而重新核对等级时不适用（§5）。
- **等级要带证据。** `blocking` 指明可达路径（调用方的 `file:line`，或域条款）或违反的合同条目。`non-blocking:contrived` 说明为什么没有域内输入能触达它：列举出的调用点，以及要发生什么改变这种构造才会出现。评审者提出等级；裁决者按与任何裁定相同的 `file:line` + 谓词标准核实。升级总是允许的；把评审者判为 `blocking` 的发现降级，要把那份证据写进处置，与拒绝一样。
- **等级改变的是处置，不改变报告。** 每条发现仍然要报告、编号，并附上各自的证据；要求评审者只报告阻断发现是范围缩减（`references/recovery.md` 的禁用措辞），L5 会拒绝。同一刻意构造类的多个变体，作为一条发现报告，在其中列举各个变体。

## 5. 关闭

一个评审点在满足以下全部条件的那一轮关闭，主 agent 运行 `review-round.sh close <point> --outcome passed --reason …`（要求最近一轮已 `result`，且 `blocking=0`、`rejected=0`、`pending` 不大于 0）：

1. reviewAgent 本轮自己的报告是 `no-changes-needed`——零条 `blocking`。reviewAgent 的结果为 `changes-requested`，当且仅当它报告了至少一条 `blocking`；它针对之前的拒绝或降级而重新提出的发现也算在内。
2. 本轮每一条跨 harness 发现都有了处置，且没有一条被接受为 `blocking`。
3. 没有标为 `requires-user-decision` 的发现在等待用户回答。等用户决定的 blocking 用 `result --pending` 记数；什么时候问、等的时候哪些部分不动，见 `prompts/main-agent.md` `## 提问与自动执行`。
4. 每个覆盖维度都已登记（增量轮登记它的三项任务：修复已落地、diff 无新问题、被拒绝的 blocking 已复核）。

关闭的另外两种出口都由用户决定：停下来交给用户时（§7），用户选择接受为遗留风险（`--outcome residual --by user`）或拆成加固任务（`--outcome split --by user`）。每次关闭写一行 `Review-Close`；已关闭的评审点再 `start` 会被拒绝，要重开先 `open`（生成一组新记录）。§4 交付核验要求每个已登记的评审点都有一条 `Review-Close`。

拒绝或降级一条 reviewAgent 的阻断发现，本身不会关闭评审点：本轮记为 `rejected`，`passed` 关不了；下一轮（增量轮同样）的 reviewAgent 拿到该处置，要么认可它，要么重新提出它，这让接受↔拒绝反复 3 轮即升级的规则保持有效。下一轮评审者认可了全部拒绝、且没有新的 blocking 时，那一轮 `result --blocking 0 --rejected 0`，评审点可以 `passed` 关闭。拒绝一直僵持到轮次上限时，按 §7 交给用户。跨 harness 发现是参考性的，有了处置就算了结。

非阻断发现不让评审点保持打开，去向按评审阶段分：

- **设计评审的 `non-blocking:normal`**——不进设计正文，只记入评审历史文件（`references/design-doc-discipline.md`）。实现者确实需要的细节写进 `<task-dir>/impl-notes.md` 的 `## 实现备注`（注明来源发现的编号），随 lane 派发，并附给实现评审，由评审者逐条核对是否落地。设计评审不随阻断修复把它们写进正文，也不为它们额外开一轮：设计正文每多一段新文字，下一轮就多一段要评审的表面。
- **实现评审的 `non-blocking:normal`**——某个阻断修复反正要开下一轮时，已接受的此类发现可以一起落地、一起评审。在一个没有阻断发现的轮次之后，主 agent 可以在每个评审点额外开一轮专门落地已接受的 `non-blocking:normal` 发现；这一轮照常 `start`、计入轮次上限，上限不够时不开。那一轮提出的任何低于 `blocking` 的内容只记录、不落地。两种落地都以不引入新机制为前提。未落地的记入遗留风险清单。
- **要加新机制才能解决的非阻断发现，先重新核对等级。** "新机制"指新增表、接口、状态，或跨模块的规则。重新核对的对象是问题，不是解法：按 §4 再问一次"按原样实现，声明域内的真实情况下会不会出错"。
  - 会出错：这条发现原先定级偏低，改判 `blocking`，附可达性证据（与任何升级相同的证据标准），计入本轮 `--blocking`，按 blocking 修复。
  - 不会出错：等级不变，记入遗留风险清单（`- Hardening Plan:` 写这个机制），后续 PR 再做，不在本任务内完成。

  - 拿不准：不改判，按"不会出错"处理。

  "想加这个机制"不是改判的理由，改判只凭可达性证据。§4 的"拿不准时按 `blocking`"只适用于评审者第一次定级，"升级总是允许"指的是附了可达性证据的升级；两条都不能用来在重新核对时把等级抬上去。
- `non-blocking:contrived`——不在本评审循环内修复，每一条都进遗留风险清单，循环继续推进。

## 6. 反复出现的类别

一条发现是同一评审点之前某一轮已修复过的某类问题的新变体（同一机制，不同构造）时，评审者标为 `recurring: <class> (rounds …)`。第二个变体的出现，就是"逐点修复不对路"的信号，裁决者不再用又一个逐点修复回应：

- 该类别在声明域之内时，要求**一个**能消除整个类别的类级修复——在不受信任的操作外面加一个完整的守卫并提供固定的安全兜底，在遍历处设深度 / 环的上限，在比较之前设一个统一的规范化点——并配一个用表格或生成器驱动整个类别的测试。
- 该类别在域之外时，在遗留风险清单中把该类别记录一次。之后的某个变体，只有当它的每一个产生者都落在该条目已经排查过的调用点之内时，才能通过指向该条目来处置，并在处置中写明这一点。由该条目没有列举到的产生者触达的变体，是一条新发现，有它自己的等级和可达性证据。

## 7. 轮次上限与提前停（快速档、标准档）

同一评审点的总轮数，含首轮：

| | design | impl | aggregate |
|---|---|---|---|
| fast | 0（不派设计评审） | 2 | 1 |
| standard | 3 | 3 | 3 |
| strict | 无 | 无 | 无 |

快速档的 impl 是 1 轮独立评审加最多 1 轮修复复核，跨 harness 与第 1 轮并发；aggregate 只在多 lane 时做一次轻量的契约一致性检查，这 1 轮同样 `cross-harness=yes`。

**第 2 轮不收敛就提前停**（标准档的每一个评审点：设计、实现、汇总）。第 2 轮的 blocking 数不为零、且不少于第 1 轮时，不开第 3 轮，先交给用户。这里的"blocking 数"取被接受的与被拒绝的之和（`blocking + rejected`），脚本的判据是第 2 轮 ≥ max(第 1 轮, 1)。第 2 轮一条都没报不算不收敛：两轮都没有新 blocking、只剩待定项时，用户回答后开第 3 轮复审是正常路径。放宽上限解决不了不收敛：再开一轮之前，用户要先看到为什么没有收敛。

**停下来交给用户**：到上限或提前停时，`review-round.sh start` 以 exit 3 拒绝开新一轮，并输出各轮走势（`status` 里这个评审点显示 `gate=needs-grant` 或 `gate=not-converging`）。主 agent 既不悄悄关闭评审点，也不自动继续，而是用一条消息交给用户，内容依次是：

1. **诊断。** 数据取自 `review-round.sh status <point>`（各轮的 `blocking / rejected / induced / pending / delta`）和本轮的裁决：
   - 各轮 blocking 走势：被接受的、被拒绝的、其中改变产品行为的，在减少、持平还是增长；
   - 各轮修订量（设计评审的 `delta`）：新写的量有没有逐轮变小；
   - 本轮 blocking 的来源，各几条：原有漏报、上一轮修订带出（含只落地一半的）、等用户决定；
   - 剩余 blocking 分成结构类和细节类，各几条。结构类指要改模块划分、接口或数据模型；细节类指某个模块内部的规则。
2. **剩余 blocking 清单**（含仍被评审者坚持、被裁决者拒绝的那些，各附双方理由）：每条的可达性和影响，属于结构类还是细节类。
3. **三个选项，附推荐和一句理由：**
   - **再开一轮**——剩余问题涉及安全或数据、真实路径上的缺陷还在减少、或者修复方案已经明确时，推荐这一项。修复方案明确的 blocking 在这一轮里落实到设计（或代码）并做增量复审，不留给下一个阶段去补。用户批准后运行 `review-round.sh grant <point> --reason <用户原话要点>`；一次授权只管一轮，下一次再交用户。
   - **接受为遗留风险**——每条写进遗留风险清单，状态注明是用户在停下时接受的，然后 `review-round.sh close <point> --outcome residual --by user --reason <用户原话要点>`。
   - **拆成加固任务**——把清单写进新任务的输入（新任务重新选档），本任务在最终报告里列出它，然后 `close <point> --outcome split --by user --reason …`。

用户的选择记入 `decisions.md`。提问后按 `SKILL.md` `## Watchdog 强制层` 声明 `user`。用户也可以选择升档（`review-round.sh tier strict --reason …`），之后按严格档规则推进。

## 8. 严格档：收口检查

严格档不设轮次上限。保留"主要问题 vs 边界或极端构造"的分级：极端构造进遗留清单，后续另开 PR 加固，不在本轮里反复对抗，也不影响主体实现。

从第 3 轮起，每满 3 轮做一次收口检查：要开第 n 轮（n = 4、7、10…），必须有一条 `round == n-1` 的 `Review-Check`——只认刚完成的这一组三轮，更早的检查不算；否则 `review-round.sh start` 以 exit 3 拒绝。检查内容：对每条未关闭的阻断发现重新检查可达性并附证据；每个反复出现的类别以及它是否得到了类级修复；每轮的 blocking 数和 behavior 数的走势。结论用 `review-round.sh check <point> --outcome <o> --reason …` 记录，`<o>` 是以下之一：

- `continue`——阻断发现都在真实路径上，并且在减少；
- `class-fix`——对反复出现的类别改用类级修复；
- `reorder`——调整加固顺序：阻碍主路径收敛的是范围内的加固工作（域确实包含的对抗性输入）时，把它移到单独的加固 lane，排在主路径之后，让主路径先关闭、提交并可用。这是在已批准设计之内安排工作顺序，由主 agent 决定。加固 lane 仍留在本任务中，并且仍要交付（`SKILL.md` `## 总目标忠实度`）；它接手的每一条阻断发现，在发现台账中有一行 `dispatched-to: <hardening lane>`，它的第一次评审派发把这些发现列为预期应落地的内容，§4 交付时逐条核实已落地；
- `escalate`——升级给用户：剩余的阻断发现取决于设计没有回答的范围或威胁模型问题，或者结论会把任何内容移出本任务。这会改变设计，由用户决定。

每次检查的结论都用一条简短消息连同理由告诉用户，长时间的循环不会悄无声息；只有 `escalate` 需要等待回答。结论是 `escalate` 时，交给用户的消息同样带 §7 的诊断和三个选项；无论在哪一轮，`start` 在拿到授权前都以 exit 3 拒绝下一轮。用户同意继续时运行 `review-round.sh grant <point> --reason <用户原话要点>`（一次一轮），选择其它两项时按 §7 `close`。编排模式下这条消息发到 worker 的 pane 和状态文件，升级通过 `ZYZ_QUESTION_FILE` 问答进行。

没有 `Tier:` 行的旧任务按严格档执行，`review-round.sh` 和 `review-gate.sh` 对它们 fail open；收口检查仍按本节由主 agent 记录在 `## 评审收口`。

## 9. 主路径优先

组织工作时，让主路径先收敛、先交付。设计时先锁定主路径及其关键约束，再处理边界情形。在实施计划中，范围内的对抗性加固作为主路径之后的独立 lane，不并入主路径的评审循环。

要用户定的问题不攒到设计批准闸门：每轮裁决完就问，依赖回答的部分在回答之前不动（`prompts/main-agent.md` `## 提问与自动执行`）。攒到闸门再问时，主 agent 只能先按推荐项改正文再送评审，评审者评的是用户没确认过的方案，同一个问题会被连续几轮重复报告。

## 10. 遗留风险清单

`<task-dir>/residual-risks.md`，基于 `templates/residual-risks.md`，写第一条时创建。它保存评审循环遗留下来的行为层面残留：每一条 `non-blocking:contrived` 发现（每个类别一条，而不是每个变体一条），每一条没有落地的行为或测试层面的 `non-blocking:normal` 发现，要加新机制才能解决、重新核对后仍是非阻断的发现（§5），以及用户在停下时（§7）接受为遗留风险的 blocking。每个条目包含：

- `- Origin:` 来源（评审点、轮次、发现编号、评审者）；
- `- Tier:` 等级和类别；
- `- Reproduction:` 一个最小的具体复现；
- `- Impact:` 影响评估——为什么当前没有域内输入能触达它（列举出的调用方），以及什么改变会让它变得可达；用户接受的 blocking 写明它的可达路径；
- `- Hardening Plan:` 加固方案（如果有评审者或角色核实过：做什么、在哪里、如何核实的），或 `none proposed`；
- `- Status:` 状态。

这份清单是之后任何加固任务的输入，某个条目要重新推导才能被那个任务使用，它就是不完整的。把清单路径传给之后的每一个评审者（reviewAgent 的派发和跨 harness 的简报），对已登记的条目指向它即可答复，而不会被重新提出；只有出现它可达的新证据时，它才作为一条新的 `blocking` 重新出现。最终报告总结它（`## 已知风险`），并提出消化它的后续工作（`## 后续工作`）。

## 11. 机械化

| 命令（`<plugin-root>/hooks/scripts/review-round.sh <cmd> [--task <task-dir>]`） | 作用 |
|---|---|
| `open <point> --stage design\|impl\|aggregate [--kind main\|aux] [--tier standard\|strict]` | 登记（或升档重开）评审点 |
| `start <point> [--full --reason …] [--docs <path>...]` | 开新的一轮；上一轮没 `result`、超过上限且没有授权、标准档第 2 轮不收敛且没有授权（§7）、严格档缺收口检查、最近一次收口检查是 `escalate` 且没有授权、或评审点已关闭时 exit 3，并输出该怎么做。design 评审点另外保存文档快照并输出修订量（§2） |
| `result <point> --blocking N --rejected R --induced I --pending P [--behavior M]` | 记录本轮结果：接受的 blocking 数、被拒绝或降级的 blocking 数、上一轮修订带出的条数、仍在等用户回答的条数、改变行为的条数（有档位的任务第 2 轮起 `--rejected`、`--induced`、`--pending` 必填） |
| `grant <point> --reason …` | 用户批准额外一轮，一次一轮 |
| `check <point> --outcome continue\|class-fix\|reorder\|escalate --reason …` | 严格档收口检查 |
| `close <point> --outcome passed\|residual\|split [--by user] --reason …` | 关闭评审点；`passed` 要求最近一轮 `blocking=0`、`rejected=0` 且 `pending` 不大于 0；`residual` / `split` 要求 `--by user` |
| `tier <fast\|standard\|strict> --reason … [--by user]` | 写档位，追加 `log/tier.md`；降档要求 `--by user` |
| `status [<point>]` | 列出评审点、轮次、上限、下一轮的模式，以及各轮的 `blocking / rejected / induced / pending / delta` |

脚本校验后原子写入 `status.md` 的 `## 评审收口`，主 agent 不手写这些行；行格式见 `hooks/README.md`。不给 `--task` 时作用于本会话的主任务（与 `expect.sh` 相同）。`review-gate.sh`（PreToolUse，只处理 review-agent 派发）核对派发 prompt 里的 `review-point=… round=… mode=…` 行和单独一行的 `Tier:`（要等于评审点的生效档位），只放行尚未 `result` 的那一轮；它只拦 Agent 派发，所以评审一律重新派发（§2）；`ZYZ_REVIEW_GATE_DISABLE=1` 只关闭这一个闸门。`cross-review.sh` 收 `--mode`，在 impl 评审点的增量轮自动跳过（`references/cross-harness.md`）。

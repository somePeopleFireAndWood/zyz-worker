# 设计文档

适用于标准档和严格档任务目录下的设计文档；快速档用 `change-note.md`，没有设计评审和评审历史。

## 两类文件

| 文件 | 放什么 | 给谁 |
|---|---|---|
| `<basename>.md` | 最终设计，按 `templates/design-doc.md` 的小节写 | 用户、lane、评审者 |
| `<basename>.review-history.md`（同级，写第一条时创建） | 每轮改了什么和为什么、被拒绝的发现及理由、设计评审的非阻断发现 | 主 agent、下一轮设计评审 |

- 模板的小节是后续流程要用的。除这几节外，正文怎么组织由 agent 按任务决定，不为了填满而加小节。
- 设计文档只记最终设计：改就改成新的终态，修订理由、轮次和"上一版错在哪"写进评审历史，不在正文里加批注。
- 评审历史不列入 `status.md` 的 `- 设计文档:`，不发给 lane 和实现评审；设计复审时把它的路径给评审者和跨 harness 简报。
- 设计拆成多份时每份各有评审历史，跨多份的条目写进索引文档的那一份。
- 设计评审的非阻断发现、要用户定的问题怎么处理，见 `references/review-closure.md` §5、§6。

## 场景与发生时再查

- `## 场景` 列主流程和正常运行会遇到的条件，每条写期望行为。评审者和测试都按它逐条走，期望行为就是验收标准。
- `## 发生时再查` 列出错看得见、不影响生产、当场能查的情形，每条一句：谁、看什么数据来判断。写了这一句就算设计完整。
- `## 范围边界` 写明哪些入口有对手。它由用户决定；用户没有亲口说过的条款列进 `### 需要你关注的细节`。
- `## 关键机制` 给用户审查，任何档位都可以填（快速档写在 `change-note.md` 的可选一节）：安全守卫、权限、数据完整性和用户点名的机制，用户可以增删。档位只决定分工：严格档里这些机制的测试由 test-agent 写，其它档位由 lane 自己写。

## 快速审阅

`## 快速审阅` 是用户批准时看的入口：`### 设计摘要` 概述模块、分工和主流程，`### 需要你关注的细节` 列难改的决定、有真实替代方案的取舍和没有用户决策就做出的假设。

- 它不进入评审：与正文不一致不算发现。
- 与正文不一致时以正文为准，按正文重写受影响的部分，不追加更正。
- 请用户批准之前按正文重写一次。

## 批准之后

实现中要改 `## 测试计划` 时把它改到新的终态，记进 `decisions.md`（涉及场景的期望行为时按 A 类问用户）。实质改变已批准的设计时重新请用户批准；之前的跳过指令不自动覆盖这一次。

# 设计文档纪律

`SKILL.md` `## 评审历史文件` 与 `## 设计文档编辑纪律` 的细则，外加 `## 快速审阅` 的维护规则。**只适用于标准档和严格档**：快速档不写设计文档，用 `change-note.md` 代替，没有设计评审，也没有评审历史文件。本文件约束的是**任务**的设计文档（位于任务目录下），不是本仓库自己的 `docs/`，也不是本身就是交付物的文档。

## 两类文件，职责不重叠

| 文件 | 职责 | 读者 |
|---|---|---|
| `<basename>.md`（每份设计文档） | 最终设计规格 | implementation-agent / test-agent / lane / 负责批准的人 |
| `<basename>.review-history.md`（其同级文件） | 修订日志：批注、拒绝理由、裁决、标为非阻断的设计文档发现、「实现中发现」条目 | 下一个 reviewAgent / 主 agent |

评审历史文件不被评审，不产生发现，可以无限增长——它是留存书面记录的正确载体。设计文档是被评审的表面，往里添加的任何内容都是一个会产生发现的新文本面。

## 评审历史文件

- 对每份设计文档 `<dir>/<basename>.md`，评审历史放在同级文件 `<dir>/<basename>.review-history.md`，写入第一条时才创建；没有评审事件的设计文档就没有评审历史文件。设计拆成多份时，每一部分各有自己的评审历史文件；跨越多个部分的条目写入索引文档的评审历史文件。设计文档本身不含 `## 评审历史` 小节。
- 评审历史文件只对设计阶段的评审循环和批准环节有意义。派发实现阶段的角色或实现评审时，只发送最终态设计文档，不附带评审历史文件，也不让这些角色去读它们。
- 不把评审历史文件列入状态文件的 `## 元数据 > 设计文档`（该列表决定下游角色加载什么）。
- 设计评审中被拒绝的发现连同理由，记入评审历史文件和 `status.md` 的 `## 发现台账`（评审点关闭后移到 `log/review-ledger.md`）。reviewAgent 标为 `non-blocking:normal` 的设计文档发现，记入同一评审历史文件，并在 `## 发现台账` 的「记入评审历史的非阻断发现」一行计数：它们只做记录，不改进设计正文，也不妨碍 `no-changes-needed`。复审时把评审历史文件路径传给 reviewAgent 和跨 harness 简报，让它们看到之前的拒绝理由。
- 评审历史文件记录的是关于设计**文档**的发现。行为层面的残留——`non-blocking:contrived` 发现、未落地的关于代码或测试的非阻断发现——记入遗留风险清单（`references/review-closure.md`）。
- 实现中发现缺失的测试点时，把 `## 测试计划` 更新到新的最终态，并在评审历史文件和状态文件里追加一条「实现中发现」。只有实质性改变已批准方案（目标、验收标准、实施计划、架构或改动文件）时，才重新打开设计批准闸门；之前记录的跳过指令不自动满足重新打开的闸门，除非它明确授权了方案改动后继续。

## 编辑纪律

- **纠正已有文字的发现，就地修改或删除那段文字来修复，绝不在旁边追加解释性批注。** 一个过时数字的正确修法是删掉它，而不是写一段话说明为什么删它。
- **指出缺失内容的发现**——缺少的需求、约束、验收标准，或规定不足的机制——通过**补上**缺失的规格来修复。这种增长是预期之中的；本纪律从不主张少写规格。
- **纠正类修复后，文档篇幅持平或缩小**——用应用本轮已接受发现前后的 `wc -c` 衡量。一轮设计评审的净效果是篇幅增长、却没有实质性设计变化，正是本规则要阻止的失败模式；因补上真正缺失的规格而增长的一轮不算。
- **"为什么改"、"上一版错在哪"、"第 N 轮订正"写进 `<basename>.review-history.md`**，不写进设计正文。轮次编号、`前版`/`previous version` 之类的引用、`订正`/`corrected` 之类的标记，都不属于最终态规格。
- **不要把针对文档文字的自检规则写进设计文档。** 跑一次 grep 没有任何成本；把 grep 写进交付物，却会让它同时成为被评审的表面、自身扫描的对象和一个新的耦合点——实测中，这样一段内容抓到了约 3 个评审漏掉的问题，自己却产生了 20 多条发现。设计文档规定的是如何检查**代码**（变异目标、正向锚点、空转分类、载体归属——由编译器和测试套件裁决）。对文档自身文字的检查是去执行的，而不是写下来的。
- **清理累积的批注时，一次清完，且不留清理痕迹。** 逐条去批注并为每次删除留一条说明，只是又一轮追加。用机械方式验证纯删除式清理：清理前后标识符和 `file:line` 坐标的集合差，只能包含文档的自我引用——丢了一个代码坐标，说明清理删进了规格。

## 横幅与快速审阅

每份设计文档开头有一条简短的横幅，写明用户是其设计者（见 `templates/design-doc.md`）。它是保留内容，不是脚手架：留在填好的文档里，让 implementation-agent、test-agent 和负责批准的人都能读到。

横幅正下方是 `## 快速审阅`——用户的审批界面，让用户不必通读整份规格就能判断总体方向：

- `### 设计摘要`——一页以内概述整个设计：有哪些模块、各自负责什么，工作如何划分，关键算法，端到端的主流程。使用与正文相同的模块名和接口名。
- `### 需要你关注的细节`——用户在批准前应该看的实现细节，每条写明原因（不可逆或难以更改的决定、有真实替代方案的取舍、对性能 / 安全 / 数据形态的影响、偏离本地惯例之处、在用户未作决定时所做的假设——包括用户没有陈述过的每一条 `## 范围边界` 条款）。没有时写 `none`，不硬凑条目，也不把它当成 `## 待解问题` 或评审历史的第二个存放处。按推荐执行的 B 类决定在 `decisions.md`，批准时一并列给用户。

**正文是权威，摘要只是地图。** 摘要过时的典型方式是有人**追加**一句更正，而不是重写已经错了的内容（在一句仍然写着"四个模块"的话后面硬接上"（第 3 轮：现为五个模块）"）。有摘要本身不是隐患，往摘要上追加而不是重写才是。

- 两者不一致时**以正文为准**：摘要才是缺陷所在，不为了迁就摘要而修改正文。
- 修复方式是**根据正文重新生成摘要中受影响的部分**，而不是只修补被发现的那一句，也不是追加一条说明。出现偏差说明摘要是从一个已不存在的设计状态推导出来的，相邻的表述也值得怀疑，所以要重新推导整个受影响的部分（模块列表、流程或某条关注条目）。
- **快速审阅不进入评审。** 快速审阅漂移不算发现，不开新的一轮；设计正文的评审完成后、请用户批准之前，主 agent 根据正文机械地重新生成一次 `## 快速审阅`，再引导用户去看它。日常编辑正文时顺手同步摘要也可以，但批准前的这次重新生成不能省。

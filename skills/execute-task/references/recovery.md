# 恢复与续做

`SKILL.md` `## 恢复进行中的任务` 的细则：接手进行中的任务、从会话记录恢复被毁的未提交工作、长期运行工作的续做、恢复卡住的角色。

## 恢复进行中的任务

接手一个已经在进行中的任务时（会话冻结或重启过），`status.md` 是最先读取的东西——而它也最可能已经过时，因为只有有人记得去写，它才会前进。信任其中任何内容之前，先拿它与会自行前进的来源交叉核对：

1. **任务分支的 `git log` / `git status`。** 提交是由工作本身写出的，不会像状态文件那样滞后。一个 `Coded: false` 的 lane 如果已有实现它的提交，说明是状态文件落后了，而不是工作缺失。
2. **拿 `lanes/<id>.md`、`subtasks/*.md` 与主文件对照。** 它们由不同的执行者在不同时间写入；不一致时，进度更靠前的那个通常是对的，而且一个 lane 文件还可能自相矛盾（某一节标记某部分已完成，后面某一行却仍把它列为待处理）。`decisions.md` 和 `log/` 里的记录也要读，它们保存了 compact 之前的用户决策和事件。
3. **只读的 fixed-pack 观察器**，用来区分"已丢失"和"仍在运行"。一个非终态的实例，如果有经过认证的 START 和一个仍在推进的 HEARTBEAT，它就是活着的——重新派发它，会让两个 agent 在同一个工作区里写同样的文件。心跳过期只是弱证据，要结合平台 / 探测状态才能做终结处理。观察器根本无法验证 catalog/runtime 时，说明 watchdog 从未启用，你也就没有任何存活证据——如实说明，不要猜。

交叉核对发现冲突时，立即把核对后的状态写进 `status.md`，标明哪些部分是根据代码重建的、而不是原本记录的。不要从一个刚证明有误的文件上悄悄继续；下一个读者会像你一样信任它。会话恢复后还要重新 `task-pointer.sh arm`（`references/watchdog.md`）。

## 从会话记录恢复被毁的未提交工作

未提交的工作丢失时（checkout/stash 事故、编辑器崩溃、一个从未进入提交的文件被删除），git 里什么都没有：从未提交过的内容不在任何 reflog、任何 stash 里，`git fsck --lost-found` 也看不到它。但 agent 写过的一切都逐字记录在它的会话记录里：

```text
~/.claude/projects/<encoded-cwd>/<session-id>.jsonl                     (main agent)
~/.claude/projects/<encoded-cwd>/<session-id>/subagents/agent-*.jsonl   (subagents)
~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl                           (Codex events)
```

每个 Write 的 `tool_use` 条目都在 `input.content` 中带有完整文件；每个 Edit 带有 `input.old_string`/`input.new_string`。恢复步骤：确定是哪个 agent 写了丢失的内容（看 `## Agent State`，或在会话记录中 grep 丢失代码里一个有辨识度的标识符），提取它对受影响文件的 Edit/Write 输入，按原始顺序重放——不凭记忆重建。这对安全敏感的代码（防护、裁决器、脱敏）尤为重要：凭记忆重建、却有细微错误的版本是一个悄无声息的绕过，比明摆着的缺失更糟。用暴露出丢失问题的那些测试验证重放结果。催生这条规则的那次事故里，正是这条路径逐字恢复了一个约 5000 字符的防护函数。

## 长期运行工作

在漫长的实现阶段，`status.md` 要保持最新：当前活动的角色、最新输出、阻塞事项、下一步。状态文件的价值取决于它最后一次写入的价值——每次状态转换都作为转换的一部分写入主文件，它从来不是一项"等有空时"再做的记账工作。两层漂移（主文件停滞而 lane 文件在前进）正是让恢复中的会话误判工作停在哪里的那种形态：曾有一个 9 个 SubTask 的任务，主文件停在 ST1，而九个 SubTask 其实都已实现、测试、评审并推送。

某个角色卡住、中断或长时间无响应时，以**续做而不是重做**的方式重启它。在长时间的多实例运行中，超时是常态；默认重做会造成 O(lane 数 × 超时次数) 的重复工作，还会留下伪装成回归的脏数据。三个步骤：

1. **先盘点。** 用 `git status` 加上资源租约表，列出被中断的角色已经在磁盘上产出了什么——写过的文件、创建的测试数据库 / fixture / 迁移、占用的端口。盘点来自磁盘，而不是被中断的上下文（它已经没了）。
2. **续做，不重建。** 把盘点结果作为续做起点放进重启提示词，写明"继续；不要重新创建以下产物"。具名的 lane teammate 用 SendMessage 让它从自己的会话记录接着做。
3. **清理残骸。** 假定被中断的运行留下了脏数据（写了一半、带固定 id 的 fixture 行会造成主键冲突，看起来和实现回归一模一样——识别特征是重跑能稳定复现，所以不是竞态）。重跑前先清理。

每个事件作为新的一行追加到 `<task-dir>/log/restarts.md`（只追加的事件列表）。没有真正的 subagent 运行时，就从状态文件恢复，并用最新的设计和状态摘要重新下发角色提示词。以相同的范围重启（下一节）。另见 [docs/conventions/long-running-state.md](../../../docs/conventions/long-running-state.md)。

## 恢复卡住的角色：绝不拿范围换交付

停滞或超时的角色会带来"好歹先从它那拿点东西出来"的压力。要避免的失败是**为了让角色能完成而缩减所要求的内容**。缩减每轮输出量总是允许的；缩减总的交付要求不允许。

- 允许：把工作拆成带标签的步骤或维度，每条消息完成一个；更小的连续编辑；先做风险最高的部分；减少需要重读的上下文。
- 在任何恢复或重新派发的指令中都不使用（中英文措辞同样）："只给总体结论"（"just the overall verdict"）、"只报最重要的 3 条发现"（"only the top 3 findings"）、"最严重的 N 条就够了"（"most severe N is enough"）、"一行结论就行"（"a one-line conclusion is fine"）、"细节就省了"（"skip the details"）、"只要总结论"、"最严重 3 条就行"、"一句话结论也行"、"只要前 3 条"，以及数量上限（"限 3 条发现"（"limit to 3 findings"）、"不超过 3 条"（"no more than 3"）、"只报阻断项"（"blockers only"）、"重点问题就行"）。L5 派发范围守卫会拒绝这类措辞；被拒绝意味着以完整范围、分步骤重新派发，而不是换个说法绕过。
- **增量复审不属于缩范围。** 评审点第 2 轮起按 `references/review-closure.md` 做的增量复审，其范围由评审点规则定义（上一轮被接受的 blocking 清单 + 修复 diff），派发里带 `mode=incremental` 标记，L5 放行。恢复一个卡住的增量复审时，同样以完整的增量范围重新派发；把一个全量轮次改成增量轮次来让评审者能完成，仍然是缩范围。
- 分阶段不是漏洞：一个设了上限的第一批交付，只有作为真正的分阶段才可以接受——承诺交付剩余部分，把步骤计划记入 `log/restarts.md`，并真正收齐每一批。没有被跟踪的"后续再继续"的承诺，是披着伪装的范围缩减；§4 交付时会核对每一批都已到达。
- 这与总目标忠实度是不同的防护面，后者守护的是用户陈述的目标和整体交付物。单个角色被要求的范围——一次评审的覆盖面、一套测试的广度、一个实现步骤的完整性——可以在不触犯总目标规则的情况下被缩小，而不完整的结果随后会看起来干干净净地通过下游每一道关卡。
- 标准做法：以同样完整的范围重新派发，明确拆成 N 步，每步一条消息，每一步写盘后再做下一步；对评审而言，按覆盖维度拆分。把这次恢复事件和步骤计划记入 `log/restarts.md`。
- 自行提出或交付缩减范围的角色，用分步拆分的做法打回，而不是接受。重试之后确实无法完成该范围时，升级给用户，说明哪些覆盖了、哪些没有——不把部分结果记为完成。

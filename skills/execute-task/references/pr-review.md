# PR 评审处理

真实 PR 上的评审评论、"changes requested"、行内讨论串和自动化发现（来自人、机器人或 CI 工具）只作参考。由主 agent 处理，一次一条。

## 逐条核实，再决定

先读它引用的代码、设计和测试，确认问题是否真的存在，再归入两类之一：

- **成立**：转给负责的 lane 修，经过正常的测试和评审后，在 PR 讨论串里回复已处理。
- **不成立**（误读、复现不了、与已批准的设计或目标冲突、超出范围）：不改，在对应的讨论串里回复不采纳和具体理由。

每条以其中一种结束；不回复也不改动不算处置。

## 升级与记录

- 发现会改变目标或 A 类设计决定时交给用户（`SKILL.md` `## 用户设计主导权`）。
- 每个决定记进 `status.md` 的 `## 发现台账`，来源写 `PR:<URL 或编号>`：接受的写改在哪里，拒绝的写发在 PR 上的理由。
- 用平台的 CLI 回复：GitHub 用 `gh pr` / `gh api`，GitLab 用 `glab mr`。没有可用的 CLI 时把理由记进状态文件并告诉用户。
